`asyncStorage.list` returns `{total, keys}` with each value cut to 200 characters (`{limit}` defaults to 50, `{prefix}` filters keys); `asyncStorage.get` returns the whole string. Pass the storage object the app uses: AsyncStorage v3's `createAsyncStorage('name')` instances are separate from the default export. Both storages are async, and `*.restore` waits for each write. A restore puts back each key the agent changed to what it held before the agent's first write to it, and deletes keys that did not exist; keys it can't put back stay pending and the call throws. A key the app has written since the agent did (a rotated token, a persisted blob) is left alone and returned as `{restored, skipped: [keys]}`. These originals live in memory: **restore before reloading**. A JS reload loses them while the values stay on disk, and `app.reload` replies with `lost` naming the restores still pending. `set` needs a key and a value (use `delete` to remove one).

SecureStore holds secrets, so `secureStore.get` returns `[redacted, N chars]` unless you pass `{full:true}`, and `bridge.pending` only says that something is pending. `secureStore.set` and `delete` can still change them, so wire it only in dev builds you trust. SecureStore cannot list its keys: `secureStoreTools(SecureStore, ['authToken'], options)` takes the keys your app uses for `secureStore.list` (set or not, and length, never the value); any other key is reachable by name with `secureStore.get`. `options` must match what the app passes to SecureStore, or the tools see a different item: one object (`{keychainService: 'auth'}`), or a function of the key for mixed options. Every read, write, delete and restore uses them, so a restored secret keeps its `keychainAccessible` and `requireAuthentication`. Keys with `requireAuthentication` show `{authRequired: true}` in `list` and are not read there, because a read prompts for Face ID or fails on a simulator without biometrics; the first `set` or `delete` of such a key still reads it once to save the old value, and changes nothing if that read fails.

A pin keeps seeded data in place through refetches until you unpin it. `net.mock('/inbox', { status: 500 })` or `{ offline: true }` fails a route (the newest mock is tried first; `{ priority }` reorders mocks from the same source); `net.entry <id>` returns a logged request with whole bodies and its headers (any header whose name contains auth, cookie, token, secret, session, password, signature or api-key is cut unless you pass `{"full": true}`: Authorization keeps only its scheme word, others at most 4 characters and a quarter of the value) and `net.mockFromLog <id> [patch]` turns its response into a mock; apps can fake a whole backend with `mockRequests` or `mockApi` from the same import, and turn on strict mode with `strictNetwork` (see [Scenarios](scenarios.md)).

**Matching requests.** A string match is a URL substring, so `"/orders"` also answers `/orders/5/items`. For anything exact use the object form, where every key given must match: `{ path: "/orders/:id" }` matches the whole path on any host and ignores the query (`:name` is one segment, `*` the rest, a trailing slash is optional either way, `/` matches a bare host, `:name` counts only as a whole segment so `/items:batchGet` is literal, matching ignores case and also tries the percent-decoded URL, no `?`, `#` or spaces; a relative URL without a leading `/` or a `//host/...` URL is not matched); `{ body: { status: "open" } }` matches a JSON request body that contains those keys (objects by key, arrays by length and position, other values by `===`; form and binary bodies never match); `{ graphql: "GetUser" }` matches a request whose `operationName` is that, in a single JSON body or the `?operationName=` query (a batched array body does not match; match it with `body`). `url` and `method` work as before. `net.mock` and `net.mocks` return `matches`, the mock in words. A body check needs the request body: for `fetch(new Request(...))` it is read from a clone, but only when its content type is JSON or text (binary bodies are never read or logged), and a mock with only `body` or `graphql` (no `url` or `path`) looks at every request, so it makes every such Request wait for that read. `net.mockFromLog` on a POST whose body was not kept returns a `warning`: the mock then matches every operation to that URL. `net.waitFor` returns once the response body has been read. In strict mode, a request that only matched mocks by URL is blocked, the error names those mocks, and `net.strict` lists blocked GraphQL requests by operation.

`net.waitFor(match, { timeoutMs?, status?, sinceId? })` waits for a request that matches the same way to finish and returns its entry. Requests already in the log count, so pass `sinceId` (an id from `net.log`) to ignore older ones. Body and graphql matches need the logged request body (JSON up to 1 MB; a Request object's body is logged only when a mock read it). `networkTools({ logSize })` sets how many requests the log keeps (default 100).

`router.navigate`, `push` and `replace` need the navigation container to wait for the new screen. They then return the route the app ended on, an object like `router.current`'s (not the href string they used to return), throw if it landed on `+not-found`, and add a `warning` when the route is not the href: a different path, or a `?key=value` of the href missing from the route's params (a redirect, or nothing happened). Before the container has mounted they return `{href, warning}`.

**React Navigation.** `navTools(navigationRef)` is for apps that use `@react-navigation/native` directly. Its tools are `nav.*`, not `router.*`, so it never clashes with `routerTools` if both are mounted. `nav.navigate Profile '{"id":3}'` goes to a route by name (and params; `{"screen": "Name"}` params reach a nested screen). In a stack, React Navigation 7 pushes unless that screen is already focused, so use `nav.popTo` (v7 only) to go back to an earlier one. `nav.push` and `nav.replace` act on the focused stack and throw when the focused navigator is tabs or a drawer, because the action would reach a parent. `nav.back` pops once. `nav.popToTop` pops the nearest stack and does nothing when it is already at its first screen, so it never pops a parent. Each waits for the new screen and returns the route the app ended on: `{ name, params, path, stack, canGoBack }`, where `path` is the names from the root navigator down to the screen and `stack` is the nearest stack's screens. A `warning` says so when the screens asked for (the whole `screen` chain) are not at the end of the path, or when `push`/`replace` changed nothing. An unknown name throws and lists the known names (those in the navigators mounted now); a screen in a navigator that has not been opened yet needs `nav.navigate Parent '{"screen":"Name"}'`. Pass `getStateFromPath` from `@react-navigation/native` and your `linking` object, with a `config`, to let `nav.navigate` take a path like `/post/7` or a URL starting with one of `linking.prefixes`. With a static config or `linking: { enabled: 'auto' }` there is no `config` to pass, so paths throw: use route names.

```ts
// in AgentBridge: tools: { ...navTools(navigationRef, { linking, getStateFromPath }) }
```

**Modals.** `router.back` pops the navigator and knows nothing about modals or sheets your app renders itself, so it can pop the screen under an open one. `router.dismiss` and `router.dismissAll` close route-based modals. For app-rendered modals there is no reliable way to press hardware back from JS (iOS has no back button, and Android's `BackHandler` cannot be fired from outside), so register a tool with your own modal system and let the agent call it:

```ts
// in AgentBridge: tools: { ...routerTools(router, { navigation }), 'modal.close': () => modalStore.getState().closeTop() }
```
