**Redux and Jotai.** They have their own prefixes (`redux.*`, `jotai.*`), so mounting them next to `storeTools` never clashes with `store.*`, and each has its own snapshot and `restore`. Both snapshot on the agent's first change (`redux.set`/`redux.dispatch`, `jotai.set`), `bridge.restore` puts it back, `*.commit` drops a snapshot, and `bridge.pending` shows what a restore would change. `redact` is by slice or atom name: `{ auth: ['token', 'user.phone'] }`, `{ session: true }` for a whole slice or atom, or a hook `(name, path, value)` that is also called for the whole value with path `''`.

`reduxTools(store, { redact })` works with `configureStore` or `createStore`. `redux.get` reads the whole state or a path from a slice (`redux.get auth user.name`, with `{pick}` and `{keys}` as in `store.get`). `redux.dispatch '{"type":"cart/add","payload":"apple"}'` sends a plain action through your reducers and middleware (no thunks; types starting `@@agent-bridge/` are reserved) and returns `{changed: [slices]}`. `redux.set auth '{"token":"abc"}'` merges into a slice without running your reducers. `set` and `restore` replace the state through one action that `bridgeReducer` handles, so wrap the root reducer where the store is created (and again after `store.replaceReducer`, which drops the wrapper). The action carries no state, so redux-logger, devtools and Reactotron never see your tokens; they see one `@@agent-bridge/replace` action. In release builds `bridgeReducer` returns the reducer unchanged. Without the wrapper they fail with that instruction and change nothing. `redux.set` merges into object slices only; array slices are refused.

```ts
const store = configureStore({ reducer: bridgeReducer(rootReducer) })
// in AgentBridge: tools: { ...reduxTools(store, { redact: { auth: ['token'] } }) }
```

Restore is per slice for `redux.set`: each slice is snapshotted the first time `redux.set` changes it, and restore puts back only those, so changes the app made to other slices meanwhile stay. A slice the app changed after the agent set it (a rotated token) is left alone and returned as `{restored, skipped: [slices]}`. `redux.dispatch` can't know what an action touches, so its first call snapshots the whole state and restore puts all of it back, including what the app changed in other slices after that. Prefer `redux.set` when you only need a value. State listeners, sagas and listener middleware see the replace action, not the actions that were undone, so side effects they started are not undone.

With redux-persist, put `bridgeReducer` inside `persistReducer`: `persistReducer(config, bridgeReducer(rootReducer))`. Then the saved copy follows a restore, because persistReducer sees a real state change. `_persist` is never snapshotted or put back. Snapshots live in memory: **restore before reloading**, since the saved copy keeps what the agent set until then.

`jotaiTools(store, { user: userAtom, count: countAtom }, { redact })` takes the store your app uses (`getDefaultStore()`, or the one under your `Provider`) and the atoms to expose by name. `jotai.list` returns each as `read-write` or `read-only` (a derived atom with no `write`). `jotai.get user name` reads a value or a path and awaits async atoms. `jotai.set count 5` sets a writable atom and returns its new value; a read-only atom is refused. A writable derived atom is set and restored through its own `write`. An atom is snapshotted on its first `jotai.set`; `jotai.restore` sets each back, newest first, and if one fails the rest are still restored and the error names it. The snapshot of an atom is read after mounting it, so `atomWithStorage` snapshots the stored value (set and restore write through to the storage). If its storage is async (AsyncStorage) and the atom isn't mounted yet, `jotai.get` it first. After each write the adapter reads the atom back: `jotai.set` refuses an atom whose value isn't the one sent (an action atom `atom(null, write)` or `atomWithReducer`: its write already ran and can't be undone, so leave those out and use your own tool), and a restore write that doesn't take is reported as failed and stays pending. An atom the app changed after the agent set it is left alone and returned as `{restored, skipped}`. Snapshots are kept by atom name, so a Fast Refresh that makes new atom objects still restores to the atom now under that name. The store must be the one your atoms live in: `<Provider>` without a `store` prop creates its own, out of reach of `getDefaultStore()`, so pass `<Provider store={store}>`. `atomFamily` members can't be named, and a derived atom that exposes a redacted atom's value is not hidden: redact it too.

`asyncStorage.list` returns `{total, keys}` with each value cut to 200 characters (`{limit}` defaults to 50, `{prefix}` filters keys); `asyncStorage.get` returns the whole string. Pass the storage object the app uses: AsyncStorage v3's `createAsyncStorage('name')` instances are separate from the default export. Both storages are async, and `*.restore` waits for each write. A restore puts back each key the agent changed to what it held before the agent's first write to it, and deletes keys that did not exist; keys it can't put back stay pending and the call throws. A key the app has written since the agent did (a rotated token, a persisted blob) is left alone and returned as `{restored, skipped: [keys]}`. These originals live in memory: **restore before reloading**. A JS reload loses them while the values stay on disk, and `app.reload` replies with `lost` naming the restores still pending. `set` needs a key and a value (use `delete` to remove one).

SecureStore holds secrets, so `secureStore.get` returns `[redacted, N chars]` unless you pass `{full:true}`, and `bridge.pending` only says that something is pending. `secureStore.set` and `delete` can still change them, so wire it only in dev builds you trust. SecureStore cannot list its keys: `secureStoreTools(SecureStore, ['authToken'], options)` takes the keys your app uses for `secureStore.list` (set or not, and length, never the value); any other key is reachable by name with `secureStore.get`. `options` must match what the app passes to SecureStore, or the tools see a different item: one object (`{keychainService: 'auth'}`), or a function of the key for mixed options. Every read, write, delete and restore uses them, so a restored secret keeps its `keychainAccessible` and `requireAuthentication`. Keys with `requireAuthentication` show `{authRequired: true}` in `list` and are not read there, because a read prompts for Face ID or fails on a simulator without biometrics; the first `set` or `delete` of such a key still reads it once to save the old value, and changes nothing if that read fails.

A pin keeps seeded data in place through refetches until you unpin it. `net.mock('/inbox', { status: 500 })` or `{ offline: true }` fails a route (the newest mock is tried first; `{ priority }` reorders mocks from the same source); `net.entry <id>` returns a logged request with whole bodies and `net.mockFromLog <id> [patch]` turns its response into a mock; apps can fake a whole backend with `mockRequests` or `mockApi` from the same import, and turn on strict mode with `strictNetwork` (see [Scenarios](scenarios.md)).

`router.navigate`, `push` and `replace` need the navigation container to wait for the new screen. They then return the route the app ended on, an object like `router.current`'s (not the href string they used to return), throw if it landed on `+not-found`, and add a `warning` when the route is not the href: a different path, or a `?key=value` of the href missing from the route's params (a redirect, or nothing happened). Before the container has mounted they return `{href, warning}`.

**React Navigation.** `navTools(navigationRef)` is for apps that use `@react-navigation/native` directly. Its tools are `nav.*`, not `router.*`, so it never clashes with `routerTools` if both are mounted. `nav.navigate Profile '{"id":3}'` goes to a route by name (and params; `{"screen": "Name"}` params reach a nested screen). In a stack, React Navigation 7 pushes unless that screen is already focused, so use `nav.popTo` (v7 only) to go back to an earlier one. `nav.push` and `nav.replace` act on the focused stack and throw when the focused navigator is tabs or a drawer, because the action would reach a parent. `nav.back` pops once. `nav.popToTop` pops the nearest stack and does nothing when it is already at its first screen, so it never pops a parent. Each waits for the new screen and returns the route the app ended on: `{ name, params, path, stack, canGoBack }`, where `path` is the names from the root navigator down to the screen and `stack` is the nearest stack's screens. A `warning` says so when the screens asked for (the whole `screen` chain) are not at the end of the path, or when `push`/`replace` changed nothing. An unknown name throws and lists the known names (those in the navigators mounted now); a screen in a navigator that has not been opened yet needs `nav.navigate Parent '{"screen":"Name"}'`. Pass `getStateFromPath` from `@react-navigation/native` and your `linking` object, with a `config`, to let `nav.navigate` take a path like `/post/7` or a URL starting with one of `linking.prefixes`. With a static config or `linking: { enabled: 'auto' }` there is no `config` to pass, so paths throw: use route names.

```ts
// in AgentBridge: tools: { ...navTools(navigationRef, { linking, getStateFromPath }) }
```

**Modals.** `router.back` pops the navigator and knows nothing about modals or sheets your app renders itself, so it can pop the screen under an open one. `router.dismiss` and `router.dismissAll` close route-based modals. For app-rendered modals there is no reliable way to press hardware back from JS (iOS has no back button, and Android's `BackHandler` cannot be fired from outside), so register a tool with your own modal system and let the agent call it:

```ts
// in AgentBridge: tools: { ...routerTools(router, { navigation }), 'modal.close': () => modalStore.getState().closeTop() }
```
