"@avasapp/agent-bridge": minor
---

`bridge.restore` can now undo MMKV and persisted-store changes after the app reloads or crashes, when you are in a session. The session keeps what `mmkv.set` and `mmkv.delete` (string values) and `store.set`/`store.call` on a zustand store with `persist` changed, and hands it to the new runtime after the reload, so a fake token you wrote before `app.reload` is still removed by `bridge.restore` and `session stop`. Nothing is rewritten at reload time: the app boots on your value. The next call reports `kept N undos across the reload`, and names values the app changed since your write, which are left alone. Other restores (stores without `persist`, queries, mocks, `onRestore`) are still lost with the usual warning. The journal stays in the session's memory and is never logged. New adapter hooks `journal`, `adopt` and `journalRev` on a `*.restore` tool let your own area opt in; `bridge.adopt` is internal: it is hidden from the tool list and refused for any caller that does not bring the session key (not access control: the runtime takes the first non-empty key it sees on each load, so two sessions on one app do not take each other's journal, and a client that is first can still read the journal, which only holds what `store.get` and `mmkv.get` already show); the journal is sent only on the reply to the call that changed it, so `bridge.journal` no longer exists. An area that never becomes ready is retried twice, then reported once as `could not re-arm after the reload` and dropped. `session stop` right after a reload still restores. Depends on the session retry change (the app-reload and lost-reply handling). Persisted stores are journaled, compared and restored per top-level key: a key you did not change is never rewritten (so a boot-time write like `launchCount` no longer hides your undo), and a key that is not plain JSON (`Set`, `Date`, class instance) or that `partialize` renames is named as `not kept across reload`. MMKV entries record the instance `id` when it has one and are skipped on a mismatch; a `mmkv.delete` whose key is simply absent after the reload is reported as already back unless the same `id` is confirmed. On MMKV v4 (no instance `id`) a `mmkv.delete` is not undone after a reload. When a persisted area and a non-persisted one were both changed, `kept N undos` can hide that the non-persisted one is lost: check `bridge.pending` after a reload.
